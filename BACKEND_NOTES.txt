WMS BACKEND NOTES
=================
Source of truth: the project plans (PRD, TRD, App Flow, Design Brief, Background
Schema, Implementation Plan). This file tracks how the backend is being built
against them. If something here disagrees with a plan, fix one of them.

1. ARCHITECTURE (TRD s1, ADR 0001)
----------------------------------
- Modular monolith: one deployable, one database, one Postgres schema per module.
- Module layers: api -> application -> domain <- infrastructure.
- Modules talk only through modules/<name>/index.ts or domain events.
- Only apps/api/src/app.ts wires modules together (composition root).
- No foreign keys across schemas. Cross-module references are ids validated
  through public interfaces.
- `npm run lint:deps` must pass on every merge.
- Every new module copies the shape of modules/inventory.

2. DECISIONS MADE
-----------------
- Single organisation, no multi-tenancy (no tenant_id). Users manage their own
  warehouse(s). Warehouse scoping still applies (warehouse_id on operational tables).
- Quantities are integers in the item's base UoM. Revisit only if needed.
- Inventory keeps text sku / location_id (business codes) and the warehouse leads every
  inventory key (ADR 0004, Accepted). Location codes are unique per warehouse; SKUs are
  organisation-wide; codes are immutable within their scope; transfers stay inside one
  warehouse.
- ERP / carrier / e-commerce vendors: not decided. Ports stay owned by the
  consuming module.

3. CONVENTIONS
--------------
- Business failures return Result<T, Error>; routes map them to 422.
- Request bodies validated with zod (400 with error.flatten()).
- Ids are UUIDs from newId(); timestamps are timestamptz (UTC).
- Migrations: one numbered SQL file per change, applied once, recorded in
  platform.schema_migrations with a checksum. Never edit an applied file; add a
  new one.
- Imports use .js extensions (NodeNext). Prettier: double quotes, semicolons,
  trailing commas, width 100.

7. OUTBOX (P0-5, TRD G2/G3)
---------------------------
- StockLedger.append(movements, events?) stores the events in platform.outbox inside
  the SAME transaction as the movements. Use cases no longer publish to the bus.
- OutboxRelay (shared/events) polls an OutboxDispatcher and hands committed events to the
  bus. Delivery is at-least-once; consumers must be idempotent. Order is not guaranteed
  once retries happen.
- PgOutbox claims rows with FOR UPDATE SKIP LOCKED in a transaction that stays open while
  the batch is delivered. A crash mid-batch rolls back, so every row stays pending.
- Failed delivery: attempts + 1, retry after exponential backoff (1s, 2s, 4s ... capped at
  5 min). After 8 failures the event moves to platform.outbox_dead_letter.
- Event payloads travel as JSON: Dates arrive as ISO strings.
- Deviations from the plans (update the docs when convenient):
  * TRD s5.4 describes pending()/markPublished(). Replaced by dispatch(), because
    SKIP LOCKED needs the claim and the delivery to share one transaction.
  * Schema doc lists outbox_dead_letter as (outbox_id, attempts, last_error, failed_at).
    name, payload and occurred_at were added because the outbox row is deleted when an
    event is dead-lettered. platform.outbox gained attempts, next_attempt_at, last_error.
- TODO: retention job (delete published rows older than 30 days, Schema doc s14);
  dead-letter replay tool; alert on dead-letter count and outbox lag (P0-9).
- The relay holds one pool connection while a batch is delivered; keep batchSize small and
  handlers fast, or give the relay its own pool.
- Run only one relay per process. Several processes are safe (SKIP LOCKED).

8. IDEMPOTENCY (P0-7, TRD s5.5)
-------------------------------
- Middleware: shared/http/idempotency.ts, mounted app-wide in app.ts after express.json().
  Applies to POST/PUT/PATCH/DELETE that carry an Idempotency-Key header (1-255 printable
  ASCII chars). GET is ignored. The key is optional for now; `required: true` makes it
  mandatory (planned for the mobile scanner, per the TRD API conventions).
- Per key and caller (user_id is 'anonymous' until the identity module exists):
  * first request: claimed, runs, response stored BEFORE it is sent to the client
  * same key + same request: stored status + JSON body replayed, header
    Idempotent-Replayed: true, nothing runs
  * same key, first request still running: 409 (Retry-After: 1)
  * same key, different request (method, url or body differ): 422
- "Same request" = sha256(method + url + body with sorted keys).
- 2xx and 4xx are kept (a 422 replays as the same 422). 5xx is NOT kept: the claim is
  released so the client can retry. Records live 24 h.
- If the idempotency store itself fails, the request fails (500) and nothing runs.
- JSON APIs only: a replay is the stored status plus JSON body.
- Known limits:
  * The record is written after the business transaction commits, not inside it. If the
    process dies exactly between the two, the key stays "in progress" and retries get 409
    until it expires (24 h) instead of risking a duplicate movement. To unstick one after
    checking the ledger by hand:
      DELETE FROM platform.idempotency_key WHERE key = '<key>' AND response_status IS NULL;
    A 500 after an ambiguous COMMIT (connection lost) can still allow one duplicate.
    Full exactly-once needs the idempotency row written inside the ledger transaction
    (unit of work); revisit before the scanner goes live (P3-4).
  * G12 (NEW, not in the TRD gap list): Express 4 does not catch errors thrown in async
    route handlers. A database error inside a route becomes an unhandled rejection and
    terminates the process (Node 15+), which also strands that request's key as in-progress.
    Fix: upgrade to Express 5 (`npm i express@5 @types/express@5`), which turns rejections
    into 500s, so the middleware releases the key. Do this before P0-9.
- TODO: schedule store.purgeExpired() (delete expired rows) once background jobs exist;
  scope keys by the real user id when identity lands.

9. LEDGER INTEGRITY (P0-8, TRD s10, PRD metric "0 rows in nightly reconciliation")
-------------------------------------------------------------------------------
- Rule (ADR 0002): for every (sku, location_id), sum(quantity_delta) over
  inventory.stock_movements must equal inventory.stock_levels.quantity.
- Pieces:
  * LedgerAuditor port + PgLedgerAuditor: one read-only SQL statement (FULL OUTER JOIN of the
    summed ledger and stock_levels). One statement = one snapshot, so a write that is half
    way through its transaction can never raise a false alarm. It also catches a movement
    with no balance row and a balance row with no movements.
  * CheckLedgerIntegrity (use case): logs at INFO when clean, at ERROR when not
    ("ledger integrity check FAILED ...", with the first 10 pairs). Lists at most 100
    pairs and says when it was truncated. The ERROR log line is the alert hook.
  * DailyJob (shared/jobs): runs it every day at LEDGER_INTEGRITY_HOUR_UTC (default 2),
    only when LEDGER_DRIVER=postgres. In-process; no memory of past runs; with several app
    instances each one runs it (harmless, but the alert repeats).
  * `npm run check:ledger` (db/check-ledger.ts): runs it once. Exit 0 = consistent,
    1 = mismatch, 2 = could not run. Use it from an external scheduler if preferred.
  * CI runs `npm run check:ledger` after the whole test suite, so every build proves the
    suite left the books balanced.
- On a mismatch: do NOT edit stock_levels by hand. Work out which side is right from the
  movements (reference_id, occurred_at), then correct with a new ADJUSTMENT movement
  (ADR 0002: corrections are new movements, never edits).
- TODO: it scans the whole ledger, fine for now. Once the ledger is partitioned by month,
  compare against stock_snapshot_daily and only re-sum recent partitions. Record each run
  in platform.job_run once the background-job tables exist (Schema doc, platform schema);
  add a metric/alert on the error log line (P0-9).

10. PRODUCTION IMAGE, HEALTH AND SHUTDOWN (P0-9, TRD G6, s9)
------------------------------------------------------------
- Build: `npm run build` uses tsconfig.build.json (apps/api, modules, shared, integrations, db;
  no tests, no web-admin) and then scripts/copy-migrations.mjs, because tsc does not emit
  the .sql files. The root tsconfig.json is type-check only (noEmit, allowImportingTsExtensions),
  so tsconfig.build.json overrides both. If the build ever complains about another inherited
  option, override it there the same way.
  Output: dist/apps/api/src/main.js, dist/db/migrate.js,
  dist/db/migrations/*.sql. Scripts needed in package.json:
    "build": "tsc -p tsconfig.build.json && node scripts/copy-migrations.mjs"
    "migrate:prod": "node dist/db/migrate.js"
- infra/Dockerfile: multi-stage; runtime stage has prod dependencies only, runs as the
  non-root `node` user, and has a HEALTHCHECK on /health/ready.
- infra/docker-entrypoint.sh runs `node dist/db/migrate.js` and then `exec`s the app, so a
  plain `docker run` migrates and serves (the exit criterion). Several containers starting
  together are safe: the runner holds a Postgres advisory lock. RUN_MIGRATIONS=false skips
  it, for a separate release step (TRD s9 proposal):
    docker run --rm -e RUN_MIGRATIONS=false <image> node dist/db/migrate.js
- .dockerignore keeps local node_modules (Windows binaries), .env and tests out of the image.
  .gitattributes pins *.sh to LF; the Dockerfile also strips CRs, since a CRLF entrypoint
  fails with "/bin/sh^M: not found".
- docker-compose: `docker compose up -d db` is unchanged. The `api` service sits behind the
  `app` profile: `docker compose --profile app up --build`.
- Endpoints (both exempt from authentication when it arrives):
  * GET /health        liveness, touches nothing
  * GET /health/ready  200 only if `SELECT 1` succeeds within 2 s and we are not shutting
                       down; otherwise 503. Failure details go to the log, not the response.
- Graceful shutdown (apps/api/src/lifecycle.ts, wired in main.ts) on SIGTERM or SIGINT:
  1. /health/ready flips to 503 and replies carry `Connection: close`
  2. the HTTP server stops accepting and drains in-flight requests
  3. outbox relay stops, then the jobs, then the database pool closes
  4. exit 0 when clean; exit 1 if a step failed or 8 s passed (Docker kills at 10 s)
  A second Ctrl+C kills the process immediately. Windows has no SIGTERM; Ctrl+C (SIGINT) works.
- Errors (Express 5): a JSON 404 handler and a JSON error handler are last in the chain.
  5xx -> {"error":"internal server error"} and a log line with the stack; 4xx keeps its message.
  This also closes G12: a crashing route no longer kills the process, and its Idempotency-Key
  is released.
- CI: the `image` job builds the image, runs it against a Postgres service, waits for
  /health/ready, checks the log shows the migrations ran, then `docker stop` must exit 0.
- Not verified here (no Docker in the authoring sandbox): the Dockerfile itself and the
  `image` CI job. The build output layout and the logic were checked; run the image once.
- Root react/react-dom dependencies: removed under P0-11 (section 12).
  No metrics yet (TRD s7): add outbox lag and readiness failures when metrics land.

11. STYLE AND CI (P0-10)
------------------------
- CI (.github/workflows/ci.yml) has three parallel jobs; any failure fails the run:
  * quality: prettier --check, eslint, tsc --noEmit, dependency-cruiser (module
    boundaries), and `npm run build` (catches a broken tsconfig.build.json early)
  * test:    real Postgres 16 service, migrate, all tests (including the Postgres contract
             suites), then check:ledger
  * image:   builds the production image, runs it, checks it migrated and became ready,
             and that `docker stop` exits 0
- Style rules: .prettierrc (double quotes, semicolons, trailing commas, width 100) and
  eslint.config.js. apps/web-admin is ignored by both: it is an independent package with its own ESLint
  config and CI job (section 12).
- Format before you push:  npm run format   (CI runs: npm run format:check)
- package.json scripts: "format": "prettier --write .", "format:check": "prettier --check ."
- .gitattributes forces LF line endings. Without it a Windows checkout becomes CRLF and
  `prettier --check` fails locally while passing in CI. After adding it, run once:
  git add --renormalize .
- Not done: a pre-commit hook (husky + lint-staged) would run format and lint on staged
  files. Optional; add if CI failures for style become common.

  own package-lock.json, own toolchain: Vite 8, TypeScript 6, ESLint 10). The root package
  is the backend only. Reasons and the conditions for revisiting: docs/adr/0003-*.md.
- Root changes that go with it:
  * remove react, react-dom, @types/react, @types/react-dom, @vitejs/plugin-react and vite

      "web:dev":     "npm --prefix apps/web-admin run dev"
      "web:build":   "npm --prefix apps/web-admin run build"
      "web:lint":    "npm --prefix apps/web-admin run lint"
- CI: a separate `web-admin` job runs npm ci, lint and build inside apps/web-admin, caching
  on its own lockfile. The frontend is still excluded from the root ESLint and Prettier.
- apps/mobile-scanner follows the same pattern when it is created.
- Node versions: the frontend toolchain needs Node 20.19 or newer. Node 20 reached its
  scheduled end of life in April 2026; CI and the Docker image still use it. Consider moving
  to Node 22 or 24 (local development already runs 24) as a small separate change.

14. INVENTORY KEYED BY WAREHOUSE (P1-7b, ADR 0004, closes G13)
--------------------------------------------------------------
- Migration 005: warehouse_id uuid NOT NULL on inventory.stock_movements and
  inventory.stock_levels; stock_levels primary key is now (warehouse_id, sku, location_id);
  the movements index is (warehouse_id, sku, location_id). Existing development rows were
  given the placeholder warehouse 00000000-0000-0000-0000-000000000001 (the P1-6 demo seed
  should reuse that id), then the column default was dropped.
- Code: StockMovement.warehouseId; StockLedger.balance(warehouseId, sku, locationId);
  AdjustStockInput and TransferStockInput carry warehouseId; the StockTransferred payload
  carries it (StockAdjusted already carries the whole movement); the ledgers lock rows in
  (warehouse, sku, location) order; the integrity check groups by warehouse.
- API (path-scoped, so a future middleware can authorise /warehouses/:warehouseId/*):
    POST /inventory/warehouses/:warehouseId/adjustments
    POST /inventory/warehouses/:warehouseId/transfers
    GET  /inventory/warehouses/:warehouseId/skus/:sku/locations/:locationId/balance
  warehouseId must be a UUID. sku and location codes: 1 to 64 characters from letters,
  digits, . _ / - (ADR 0004). The old /inventory/adjustments style paths are gone.
- Tests: the stock-ledger contract and the inventory e2e tests have regression cases for two
  warehouses sharing a location code (checked by temporarily making the in-memory key ignore
  the warehouse: three tests fail). The Postgres auditor tests include "flags only the
  warehouse whose balance drifted".
- Still to do (later migrations): length and charset CHECK constraints on the code columns;
  P1-3 and P1-4 enforce per-warehouse location and organisation-wide SKU uniqueness
  (case-insensitive) and expose the lookups that P1-5 validates against.
- Schema doc edits outstanding: stock_levels key and stock_movements index gain warehouse_id
  first; section 14 items 1 to 3 closed.

15. LOCATIONS MODULE (P1-3, ADR 0004)
-------------------------------------
- Tables (schema `locations`, migration 006): warehouse, zone, location_type, storage_class,
  location, location_capacity, location_storage_class. Reference rows are seeded: types BIN,
  PALLET, FLOOR, STAGING; classes AMBIENT, COLD, FROZEN, HAZMAT.
- ADR 0004 rules live in the database: codes match ^[A-Za-z0-9._/-]{1,64}$; warehouse, type and
  class codes are unique organisation-wide, zone and location codes per warehouse, all
  ignoring case; triggers forbid changing a code or moving a zone/location to another
  warehouse; a composite foreign key makes a location's zone belong to the same warehouse.
- Every mutable row has the audit columns (created_by/updated_by stay null until identity,
  P1-1/P1-2) and an optimistic-lock `version`: PATCH must send it; a stale one gives 409.
- Public interface (modules/locations/index.ts): getWarehouse(id), getLocation(warehouseId,
  code) (exact match), exists(warehouseId, code) (exists AND active AND warehouse active).
- HTTP: see the README. Warehouse-scoped paths so one middleware can authorise them later.
- Choices beyond the Schema doc (confirm or adjust): location_type and storage_class are
  organisation-wide; warehouse.status ACTIVE/INACTIVE; location.status AVAILABLE/BLOCKED
  (operational) plus is_active (retired); zone types RECEIVING, STORAGE, PICKING, PACKING,
  SHIPPING, QUARANTINE; capacity weight/volume are numeric(12,3). Not built yet: slotting
  rules and dock doors (later phases).
- For P1-5 (inventory validation): a retired (inactive) location must still allow stock to be
  moved OUT of it, otherwise its remaining stock gets stuck. Reject new stock INTO inactive
  or unknown locations, and refuse retiring a location that still holds stock once inventory
  can be asked (open design point).
- Tests: tests/contract/locations-repository.* (both adapters), tests/e2e/locations*.test.ts,
  tests/e2e/locations-schema.pg.test.ts (checks the constraints and triggers in Postgres).
