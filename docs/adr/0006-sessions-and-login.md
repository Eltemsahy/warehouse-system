# ADR 0006: Login with opaque session tokens

- **Status:** Accepted
- **Context:** The PRD (IDN-1) asks for sign-in with sessions, and the TRD (section 6) asks for rate limiting on authentication. A user who is disabled or signs out must lose access at once; warehouse staff share handhelds, so a lost or shared device must be cut off quickly.
- **Decision:**
  1. **Sessions are opaque random tokens, not JWTs.** A token is `wms_` plus 32 random bytes in base64url. The database keeps only its SHA-256 hash, so a leaked database does not leak usable tokens. Plain SHA-256 is enough because the token is 256 random bits; there is nothing to brute-force.
  2. **Every request checks the session in the database.** Logout, disabling a user, an administrator's password reset and a forced sign-out all take effect on the very next request. The price is one lookup per request, which a cache can absorb later if it ever matters.
  3. **A session lasts 12 hours from login, with no sliding renewal and no refresh tokens.** That covers a shift. A shorter or longer lifetime is the `sessionTtlMs` option.
  4. **Clients send `Authorization: Bearer <token>`.** The token is returned once, by `POST /identity/login`, with `Cache-Control: no-store`.
  5. **Sessions end when the account changes.** Disabling a user, resetting their password as an administrator, or changing their own password (all sessions except the current one) revokes sessions. Re-enabling a user never revives old sessions.
  6. **Login answers bad credentials identically.** A wrong password, an unknown username and a disabled account give the same 401, after the same hashing work (a dummy hash stands in for unknown users).
  7. **Failed attempts are limited.** Five failures for a username in 15 minutes lock that username (429 with `Retry-After`); 20 failures from one address lock that address. A successful login resets the username count but not the address count, so a valid account cannot be used to wipe an attacker's tally. Attempts refused while locked are not recorded, so waiting out the window always unlocks. Changing your own password counts against the same limits.
  8. **Attempts are recorded in `identity.login_attempt`,** which is never updated. Times come from the application clock so the rules can be tested.
  9. **The identity routes are left out of the idempotency middleware.** Their requests carry passwords and their responses carry tokens, which must never be stored. Their writes are safe to repeat anyway: usernames are unique, role grants are idempotent and updates carry versions.
  10. **The per-address limit needs the real client address.** Behind a reverse proxy, set `TRUST_PROXY` to the number of proxies, or every client shares the proxy's address and one bad actor locks everyone out.
- **Consequences:** Locking by username lets someone who knows a username keep that account locked out by failing on purpose. That is the usual trade-off; the lock lasts at most 15 minutes per burst and an administrator can still act. Nothing deletes old sessions or login attempts yet: a retention job comes later, and `identity.session` will gain a nullable `device_id` when device registration is built. Route protection (checking the token and the user's access on every other route) is the next step; until then only the identity routes that need a signed-in user read the token.
