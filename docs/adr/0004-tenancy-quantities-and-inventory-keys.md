# ADR 0004: Tenancy, quantities and inventory keys

- **Status:** Proposed (items 1 and 2 are settled; item 3 awaits the owner's confirmation)
- **Context:** The Schema doc (section 14) leaves three decisions open, and Phase 1 (locations, catalog, identity, and inventory validating against them) cannot start cleanly without them. Reading the Schema doc for the third one exposed a conflict: `location.code` is unique only per warehouse (`UNIQUE(warehouse_id, code)`), but inventory keys its balances on the location code alone (`stock_levels` primary key `(sku, location_id)`). With two warehouses that both have a location `A-01`, their stock would merge into one balance. A first draft of this ADR fixed that by making location codes unique across the whole organisation. The owner rejected it: it forces a naming convention onto users to work around a limitation of the data model, and it breaks as soon as a second site already has labels that collide. It also contradicts the Schema doc's own warehouse scoping rule ("operational tables carry `warehouse_id`, indexed first, for RBAC and partitioning").
- **Decision:**
  1. **Tenancy:** one organisation per deployment, with no `tenant_id`. A user may have access to several warehouses, and `warehouse_id` scoping on operational tables stays. A second organisation gets its own deployment and database; the schemas have no cross-schema foreign keys, so they can be moved.
  2. **Quantities:** whole numbers, in the item's base unit of measure. Conversions (for example cases to each) happen at the edges, using the catalog's UoM tables; the ledger stays integer.
  3. **Inventory keys:** inventory keeps text business codes, and the warehouse becomes part of every inventory key:
     - **SKUs** are organisation-wide: one unique text code per item, because the catalog is organisation-level.
     - **Location codes** are unique **per warehouse**, as in the Schema doc. Two warehouses may both have an `A-01`.
     - **The warehouse leads every inventory key and index**, following the Schema doc's scoping rule: `stock_levels` becomes `PRIMARY KEY (warehouse_id, sku, location_id)`, and `stock_movements` gets `warehouse_id NOT NULL` with its index on `(warehouse_id, sku, location_id)`. `warehouse_id` is the warehouse's uuid, a soft reference validated through the locations public interface.
     - **Requests state the warehouse.** Once identity exists, the current warehouse comes from the session or the registered device and is checked against the user's warehouse access (the same value authorisation needs anyway). Until then it is a field in the request.
     - **Codes are immutable within their scope.** `stock_movements` is append-only, so renaming a code would mean rewriting history. To retire a SKU or location, mark it inactive. To change a code, create the new one and transfer the stock. A location never moves between warehouses; that would be a new location. Alternative names (barcodes, supplier codes) live in the catalog and resolve to the canonical code.
     - **Exact match, case-sensitive, trimmed**, 1 to 64 characters from letters, digits, dot, underscore, hyphen and slash. The locations and catalog modules also enforce case-insensitive uniqueness within the scope (`lower(code)`, per warehouse for locations and organisation-wide for SKUs), so look-alikes such as `a-01` and `A-01` cannot both exist in one warehouse.
     - **Validated on write** through the catalog and locations public interfaces (P1-5): an adjustment or transfer for an unknown or inactive SKU, location or warehouse is rejected. History for retired codes stays valid.
     - **Transfers stay inside one warehouse for now.** Moving stock between warehouses needs an in-transit step and is a separate feature.
- **Alternatives considered for 3:**
  - _Organisation-wide location codes_ (the first draft). The simplest keys, but it pushes a naming convention onto users and conflicts with the Schema doc. Rejected.
  - _UUID location keys with code lookups._ Renames become free and the key is unambiguous, but the ledger becomes opaque to people, the ERP and audits, every read needs a lookup in another module, and scanners must resolve a barcode to an id before each operation. It stays a valid later move if immutable codes prove too restrictive.
- **Consequences:**
  - The Schema doc needs three edits: the `stock_levels` key and the `stock_movements` index gain `warehouse_id` first, and section 14 items 1 to 3 are closed. The location uniqueness rule stays as written.
  - Inventory needs a refactor before Phase 1 builds on it: migration 005 adds `warehouse_id` to both tables (existing development rows get a placeholder warehouse, then the default is dropped); `StockMovement`, the `StockLedger` port, both use cases, the routes, the event payloads, the ledger integrity check (grouped by warehouse), the contract tests and the README gain the warehouse.
  - P1-3 (locations) owns per-warehouse code uniqueness and immutability and exposes a lookup that returns a location's warehouse and whether it is active. P1-4 (catalog) does the same for SKUs.
  - A later migration adds length and charset `CHECK` constraints on the code columns.
  - **Revisit** quantities if items sold by weight or length appear: either choose a smaller base unit (grams) or migrate the quantity columns to `numeric`, which rewrites a large ledger, so decide before volumes grow. **Revisit** tenancy if a second organisation must share a deployment. **Revisit** the UUID option if renaming codes becomes a regular need.
