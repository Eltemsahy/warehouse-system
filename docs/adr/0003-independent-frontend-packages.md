# ADR 0003: Frontends are independent packages, not npm workspaces

- **Status:** Accepted
- **Context:** The root `package.json` carried `react`, `react-dom`, `@vitejs/plugin-react` and Vite 5 although the API has no UI. `apps/web-admin` is a separate package with its own lockfile and a newer toolchain (Vite 8, TypeScript 6, ESLint 10), while the root runs TypeScript 5 and only has Vite 5 because Vitest 2 depends on it. The root `tsc` also compiled `web-admin`'s sources with the root's older TypeScript and a root-level `jsx` setting, so two toolchains judged the same files. Two options were considered: npm workspaces (one install, one lockfile, but two diverging toolchains in one dependency tree, workspace metadata that the API's Docker build would have to handle, and both lockfiles rewritten), or independent packages with the UI dependencies removed from the root.
- **Decision:** Independent packages. Each app owns its `package.json`, lockfile, toolchain and scripts. The root package is the backend only: its `tsconfig.json` covers only backend folders, and it has no React or Vite dependencies of its own. The root offers thin `web:*` scripts that delegate with `npm --prefix`. CI has a separate `web-admin` job that installs, lints and builds the frontend on its own.
- **Consequences:** The API image never sees frontend dependencies, each toolchain upgrades on its own schedule, and a frontend failure cannot break backend tooling. The cost is two installs (`npm run web:install` covers it) and no shared code between packages. Revisit and move to npm workspaces when two or more packages need shared TypeScript code (for example a typed API client used by both `web-admin` and `mobile-scanner`), or when drift between their dependencies starts to hurt. `apps/mobile-scanner` follows the same pattern when it starts.
